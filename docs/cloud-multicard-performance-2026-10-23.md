# 多卡片展开性能优化（2026-10-23）

用户反馈多张展开卡片低帧率，后明确要求停止手机调试。收到要求后停止真机采样，后续仅做本地代码回归和签名打包。最终包不再推送手机。

## 定位与改动

此前采集的两卡片 trace 显示，同一动画进度会被 ValueAnimator 更新及多个原生视图树的 preDraw 重复提交。一次五轮展开/收起的探索采样中，frame 调用 4379 次、输入区域更新 22294 次。不同 trace 的业务卡片及锁屏状态存在变化，不能把这些总数当作严格的帧率对照结论。

此次基于确认的重复调用路径做三项优化：

1. Motion 记录已提交的时钟进度。多个 native preDraw 观察到同一进度时，只重申隐藏原生画面，不重算整组轨迹、材质、几何及输入区域。目标尺寸重定向时清除该记录，保证新轨迹仍会提交。
2. 新增 CloudFrameBatch，把同一个同步 render tick 内的多卡片 geometry/opacity 输入更新合并。所有卡片写完后，逐卡片计算一次局部区域，最后合并到主窗口。批次可嵌套，finally 确保异常后退出延迟状态；真实 beginTransition(close)、窗口卸载及触摸转发等批次外事件仍立即更新输入。
3. 同一组卡片只由主 surface 监听共享的原生树；一次回调统一同步整组。独立呈现树也只注册一个组级绘制前反馈回调。保留每张卡片的原生内容刷新、布局监听、拖动缩放反馈和命中区域，不改变动画时长、错峰节奏、模糊或圆角外观。

用于定位的临时 android.os.Trace 包裹已从最终源码中移除。

## 验证

- 新增同进度 native traversal 不得重复写入画面的回归，修复前实际失败，修复后通过。
- 三卡片测试覆盖三个原生视图分别遍历时不重复提交，原生隐藏仍有效；原有多卡片错峰、位置、收起、反转、目标重定向继续通过。
- 新增 CloudFrameBatch 的 3 项 JUnit：八卡片多次写入只请求一次提交、嵌套回调不能提前提交、异常清理后后续输入仍立即处理。初始未合并实现的三项测试均实际失败。
- 全量 Hook 回归、文字渲染回归、Debug/Release 构建、JUnit 及 Release lint 的最终输出分别保存在 .local/cloud-multi-final-effects.log、.local/cloud-multi-final-text.log、.local/cloud-multi-final-build.log。

最终组级监听优化尚未完成有效真机帧率复测：当时手机处于安全锁屏，随后用户要求停止调试。本文不宣称已达到固定 FPS 或具体帧率提升比例。
